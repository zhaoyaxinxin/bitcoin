二、代码内容与 coinExchangeScript 的工作原理            （对应练习 A、B）
================================================================================

2.1 我实现的三个函数

    本次作业需要实现的只有 swap_scripts.py 中的三个函数，其余文件仅填写参数：

        coinExchangeScript(pk_sender, pk_recipient, hash_of_secret)
            生成交换交易的锁定脚本（ScriptPubKey），规定该 UTXO 只能被两种方式之一花费。

        coinExchangeScriptSig1(sig_recipient, secret)
            知道秘密 x 的接收方赎回时使用的解锁脚本。

        coinExchangeScriptSig2(sig_sender, sig_recipient)
            发送方与接收方共同签名、超时退款时使用的解锁脚本。

2.2 ScriptPubKey 的结构与真实反汇编

        OP_IF
            OP_HASH160  <H(x)>  OP_EQUALVERIFY  <pk_recipient>  OP_CHECKSIG
        OP_ELSE
            <pk_sender>  OP_CHECKSIGVERIFY  <pk_recipient>  OP_CHECKSIG
        OP_ENDIF

    Alice 的 BTC 交换交易实际生成的脚本（131 字节）反汇编如下：

        63                 OP_IF
        a9                 OP_HASH160
        14 853b7750…5720   PUSH 20 字节  H(x)
        88                 OP_EQUALVERIFY
        21 020f8309…6a63a  PUSH 33 字节  Bob 的 BTC 压缩公钥（recipient）
        ac                 OP_CHECKSIG
        67                 OP_ELSE
        21 022d9a57…d721ea PUSH 33 字节  Alice 的 BTC 压缩公钥（sender）
        ad                 OP_CHECKSIGVERIFY
        21 020f8309…6a63a  PUSH 33 字节  Bob 的 BTC 压缩公钥（recipient）
        ac                 OP_CHECKSIG
        68                 OP_ENDIF

    BCY 侧结构完全相同，只是 (sender, recipient) 换成 Bob 和 Alice。
    这正是整套协议的核心：两条链各自锁定一份资产，但用同一个 H(x) 绑定。

2.3 两条花费路径的栈推演

    （1）哈希锁分支：接收方持有 x

        ScriptSig = [sig_recipient, x, OP_TRUE]
            栈 = sig_recipient | x | true
            OP_IF 弹出 true → 进入 IF 分支，栈 = sig_recipient | x
            OP_HASH160 把 x 压成 H(x)，与脚本中的 <H(x)> 由 OP_EQUALVERIFY 比较
            PUSH pk_recipient 后 OP_CHECKSIG 验证 sig_recipient → 真

        也就是说，想走这条路，必须同时具备「x 的原像」和「接收方的签名」。

    （2）双签退款分支：发送方与接收方共同签名

        ScriptSig = [sig_recipient, sig_sender, OP_FALSE]
            栈 = sig_recipient | sig_sender | false
            OP_IF 弹出 false → 进入 ELSE 分支，栈 = sig_recipient | sig_sender
            PUSH pk_sender + OP_CHECKSIGVERIFY 验证 sig_sender
            PUSH pk_recipient + OP_CHECKSIG 验证 sig_recipient → 真

        这条路径完全不需要 x，只需要两个有效签名。

    注意参数顺序：CScript(list) 的语义是「列表靠后的元素最后入栈、位于栈顶」。
    因此 coinExchangeScriptSig2 的参数写作 (sig_sender, sig_recipient)，
    返回列表却必须是 [sig_recipient, sig_sender, OP_FALSE]——写反则验证失败。

2.4 两个设计取舍

    （1）为什么用 OP_CHECKSIGVERIFY + OP_CHECKSIG，而不用 OP_2 OP_CHECKMULTISIG？

        OP_CHECKMULTISIG 有一个历史遗留缺陷：执行时会额外弹出一个栈元素，因此
        ScriptSig 必须在末尾多压一个 dummy 值（OP_0），且签名顺序必须与公钥顺序
        严格对应。而这里只需要「两个签名都有效」，用 CHECKSIGVERIFY 串联两次单签
        能达到完全等价的效果，栈布局更直观，也不会踩到 dummy 元素的坑。

    （2）为什么脚本里没有时间锁（OP_CHECKLOCKTIMEVERIFY）？

        因为 coinExchangeScript 的函数签名只有三个参数
        (public_key_sender, public_key_recipient, hash_of_secret)，
        没有任何位置可以传入锁定期。本方案的时间锁由退款交易自身的 nLockTime
        字段承担：退款交易在构造时就设定 nLockTime = 当前链高度 + 锁定期，
        在该高度之前矿工不会打包它。

三、Alice 为什么总能拿回钱？为什么 1/2 multisig 不行？    （对应练习 B）
================================================================================

3.1 三个必要条件

    以 Alice 用 coinExchangeScript 向 Bob 发送 BTC 为例。Alice 能保底取回资金，
    依赖 swap.py 中三条同时成立的安排：

    （i）退款交易先签后广播

        时序是：
            构造 T1（交换交易，先不广播）
            构造 T1'（退款交易，输出给自己）
            请 Bob 对 T1' 签名，拿回 bob_signature
            确认拿到签名之后，才广播 T1

        「把钱锁出去」这一动作，发生在「已经持有退款所需签名」之后。
        因此即使 Bob 此后彻底失联，Alice 手上也已有完整的退款凭据。

    （ii）退款交易带 nLockTime

        T1' 的 nLockTime = 5,261,067（当前高度 + 5）。在到期之前它不可被打包，
        这既给了 Bob 足够的赎回时间窗，也防止 Alice 一边锁币一边立刻撤资。

    （iii）退款分支不需要 x

        退款走的是 ELSE 分支，只要求 Alice 和 Bob 各出一个签名。这意味着即使 x
        永远不公开，这条路径依然可用。如果退款也依赖 x，那么「x 没泄露」就会同时
        意味着「谁都取不回钱」，协议失去退路。

    三者合起来：Bob 老实赎回，Alice 拿到 x 去赎 BCY；Bob 不赎回，5 个区块后
    Alice 单方面广播 T1' 取回 BTC。两条路都不亏。

3.2 为什么简单的 1/2 multisig 解决不了

    （1）缺少哈希锁，两条链之间没有任何密码学绑定

        原子性的来源是「同一把钥匙同时打开两把锁」。哈希锁强制：任何一方在某条链
        上行使花费权时，必须把 x 明文写进 ScriptSig，从而**公开**秘密，对方读到
        即可在另一条链复用。1/2 multisig 中没有 x 这个共享变量，两条链上的交易
        彼此独立——「我在这条链拿了钱」不会触发「你也能在那条链拿钱」。

    （2）若两笔都设成 2-of-2，协议会卡死

        双方互相等待对方先行动，任一方都可以单方面拒绝签名使协议永久停滞。
        没有时间锁时已锁入脚本的币将永远取不出；即便加上时间锁，2-of-2 也只是
        「要么双方同意、要么都干等」，退化成普通托管合约，失去了「单方即可完成
        赎回」的原子性。

    （3）若放宽成 1-of-2，则先动者恒占优势

        Alice 可以在 BCY 链上先花掉 Bob 给的币（她只需自己签名），然后拒绝在
        BTC 链上履行；反向亦然。没有任何机制强迫她交出 x，也没有机制让 Bob 追回
        已花掉的 BCY，结果是「谁先动谁安全，后动者损失本金」。

    结论：原子性不是由多签的门限值提供的，而是由「哈希锁（绑定两笔交易）+
    时间锁（给守约方退路）」的组合提供的。

四、交易内容与先后次序，以及背后的设计原理             （对应练习 C）
================================================================================

4.1 六笔交易一览

  BTC Testnet3
  --------------------------------------------------------------------------
  T1   交换交易   Alice 的 UTXO(19,738) → 交换脚本   输出 19,638 聪
       锁定脚本 = coinExchangeScript(Alice, Bob, H(x))，Bob 凭 x 可取，
       或 Alice+Bob 双签可取
  T1'  退款交易   T1:0 → Alice 地址                  输出 19,538 聪
       nLockTime = 5,261,067，需 Alice+Bob 双签
  T3   赎回交易   T1:0 → Bob 地址                    输出 19,538 聪
       Bob 用 x 走哈希锁分支

  BCY Testnet
  --------------------------------------------------------------------------
  T2   交换交易   Bob 的 UTXO(50,000) → 交换脚本     输出 49,900 聪
       锁定脚本 = coinExchangeScript(Bob, Alice, H(x))
  T2'  退款交易   T2:0 → Bob 地址                    输出 49,799 聪
       nLockTime = 2,622,058，需 Bob+Alice 双签
  T4   赎回交易   T2:0 → Alice 地址                  输出 49,799 聪
       Alice 用 x 走哈希锁分支

4.2 先后次序

      Alice 侧                                         Bob 侧
      ------------------------------------------------------------------
      1. 生成 x，算出 H(x)，x 自己保留
      2. 构造 T1（不广播）
      3. 构造 T1'（nLockTime = 高度+5，不广播）
      --------------------------------------------------> 4. 对 T1' 签名
      5. 收下 bob_signature
      6. 广播 T1        ← 此刻币才真正锁出，且已有退款后路
      --------------------------------------------------> 7. 构造 T2、T2'
      8. 对 T2' 签名并交给 Bob
      --------------------------------------------------> 9. 广播 T2
      10. 广播 T4 取走 BCY —— x 随之写到链上
      --------------------------------------------------> 11. 从链上读出 x，广播 T3 取走 BTC

    核心约束：**签名永远先于广播**。任何一方把自己要广播的交易发出去之前，必须
    已经拿到对方对自己退款交易的签名。

4.3 设计原理

    （1）为什么退款也要双方签名，而不让发送方单签即可？

        如果退款只需 Alice 单签，她可以先广播 T1 让 Bob 看到币，随即广播 T1'
        把钱撤回，Bob 来不及反应。要求 Bob 也签名，等于让 Bob 在「这笔退款会生效」
        这件事上留下共同责任；同时 Bob 也无法独自撤回 T2。

    （2）为什么 alice_locktime 必须大于 bob_locktime？

        锁定期决定谁先获得「可以先撤」的主动权。令 Bob 的窗口（3 块）先于
        Alice 的（5 块）到期，实际效果是给 Alice 更长的赎回窗口：她在前 5 块内
        任何时刻赎回 BCY 都还来得及，而 Bob 必须等到第 3 块之后才能撤。
        若反过来，就可能出现「Alice 还没赎回，Bob 已撤资离场」的竞态。

    （3）为什么用绝对高度 nLockTime？

        作业框架给出的是绝对锁定语义「该高度之前交易不合法」，配合
        「当前高度 + 偏移」使用，等价于相对延迟且实现简单。代价是高度必须填准，
        填低了会让退款交易立即生效、时间锁形同虚设。

五、成功与失败时数字货币的流转                        （对应练习 D）

5.1 成功：x 正常公开（alice_redeems = True）

    BTC 链                                    BCY 链
    --------                                  --------
    Alice 的 UTXO 19,738
        │ T1
        ▼
    交换脚本锁定 19,638                       Bob 的 UTXO 50,000
        │                                          │ T2
        │                                          ▼
        │                                     交换脚本锁定 49,900
        │                                          │
        │                                          │ T4（Alice 持 x，明文写入 ScriptSig）
        │                                          ▼
        │                                      BCY 归 Alice  49,799
        │                                          │
        └──────── x 从 BCY 链上被读出 ◄────────────┘
        │ T3（Bob 用同一 x）
        ▼
    BTC 归 Bob  19,538

    结果：Alice 付出 0.00019738 BTC，得到 0.00049799 BCY；
          Bob   付出 0.0005 BCY，得到 0.00019538 BTC。
    两条链各完成一次所有权转移，双方都无需信任对方。

5.2 失败：x 从未公开（alice_redeems = False）

    BTC 链                                    BCY 链
    --------                                  --------
    T1 交换脚本锁定 19,638                    T2 交换脚本锁定 49,900
        │                                          │
        │  x 始终留在 Alice 本地内存，未上链         │
        │                                          │
        │ 等至高度 5,261,067                        │ 等至高度 2,622,058
        ▼                                          ▼
    T1' 退款（Alice+Bob 双签）                T2' 退款（Bob+Alice 双签）
    19,538 聪归 Alice                          49,799 聪归 Bob

    结果：双方各自取回本金，仅损失手续费（每笔 100 聪）。
    由于 x 从未上链，两条链上的哈希锁分支都不可用，只能走 ELSE 分支。

5.3 恶意情形

    情形 1：Alice 赎回 BCY 后赖掉 BTC？
        不可能。赎回 BCY 时 x 已写入链上交易，Bob 读到即可花费 BTC 那笔，
        不需要 Alice 配合。Alice 想赖账只能永远不赎 BCY，那她一分也拿不到。

    情形 2：Bob 拿到 x 后不赎 BTC，改去抢 BCY？
        无意义。T2 的哈希锁分支只认 Alice 的签名，Bob 是发送方，只能走 ELSE
        分支且需要 Alice 签名，他既取不走 BCY，也不影响 Alice 已到手的钱。

    情形 3：Alice 广播 T1 后立刻想撤回？
        她只能广播 T1'，而 T1' 的 nLockTime 是 5,261,067，期限未到时不会被
        打包，且还需要 Bob 的签名。等期限到了，Bob 早有赎回机会。

    情形 4：某一方在 x 公开后同时抢两条链？
        抢不到。两条链的脚本把「谁能花」写死了：BTC 锁给 Bob（哈希分支）+
        Alice/Bob（退款分支），BCY 锁给 Alice（哈希分支）+ Bob/Alice（退款分支）。
        x 只解锁对方那条链，自己这条链仍需自己的签名。

    综合来看：任何一方都无法在对方受损的前提下获利，因此理性的双方都会选择
    完成交换——这正是原子性的含义。

七、实现说明与已知问题
================================================================================

7.1 金额与手续费

    tx_fee = 0.000001（100 聪）。代码不做找零，因此 amount_to_send 必须等于所花
    UTXO 的实际金额，差额自动成为矿工费。双方的 UTXO 分别只有 19,738 与 50,000
    聪，若沿用模板默认的 tx_fee = 0.001，退款金额会变成负数。

7.2 关于 1 聪的偏差

    T2' 与 T4 的金额为 49,799 聪，理论值 49,800 聪。原因是
    0.0005 − 2×0.000001 在双精度浮点下得到 0.000497999999999999，
    经 int() 截断后少 1 聪。交易本身合法（矿工费 101 而非 100 聪），
    不影响脚本验证与协议正确性。

7.3 关于链高度的取值来源

    PDF 建议使用 live.blockcypher.com 查询高度。实测发现 BlockCypher 的
    btc/test3 节点已停止同步：其返回的区块高度停留在 4,997,970，且一周内区块
    哈希不变，而真实 testnet3 已到 5,261,062。若照抄该值，refund 交易的
    nLockTime 会落在过去，时间锁失效。故 BTC 高度改用
    https://mempool.space/testnet/api/blocks/tip/height，BCY 高度仍用
    https://api.blockcypher.com/v1/bcy/test（该节点同步正常）。

7.4 关于 BlockCypher 账户

    作业要求注册 BlockCypher 获取 API token，但 accounts.blockcypher.com 的
    注册入口目前返回 404，新账户无法创建。BCY 密钥改为按 keys.py 模板既有的
    CBitcoinSecret.from_secret_bytes 形式在本地生成（32 字节随机数），
    密码学上与 API 返回的私钥等价，不影响脚本与验证。
