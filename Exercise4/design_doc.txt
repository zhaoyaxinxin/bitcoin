================================================================================
一、代码内容与 coinExchangeScript 的工作原理（对应练习 A、B）
================================================================================

1.1 三个函数的分工

    coinExchangeScript(public_key_sender, public_key_recipient, hash_of_secret)
        生成交换交易的 ScriptPubKey，即锁定脚本。它规定了一个 UTXO 只能被两种方式之一花费。

    coinExchangeScriptSig1(sig_recipient, secret)
        生成"知道秘密 x 的接收方"赎回时使用的 ScriptSig，走哈希锁分支。

    coinExchangeScriptSig2(sig_sender, sig_recipient)
        生成"发送方 + 接收方双签"取回时使用的 ScriptSig，走多签退款分支。

1.2 ScriptPubKey 的结构

最终生成 12 个 opcode：

    OP_IF
        OP_HASH160  <hash_of_secret>  OP_EQUALVERIFY  <pk_recipient>  OP_CHECKSIG
    OP_ELSE
        <pk_sender>  OP_CHECKSIGVERIFY  <pk_recipient>  OP_CHECKSIG
    OP_ENDIF

实测反汇编（Alice 向 Bob 发送 BTC 时生成的实际脚本）：

    63                 OP_IF
    a9                 OP_HASH160
    14 853b77...5720   PUSH 20 字节  H(x)
    88                 OP_EQUALVERIFY
    21 03c168...1108   PUSH 33 字节  Bob 压缩公钥（recipient）
    ac                 OP_CHECKSIG
    67                 OP_ELSE
    21 038a3b...0470   PUSH 33 字节  Alice 压缩公钥（sender）
    ad                 OP_CHECKSIGVERIFY
    21 03c168...1108   PUSH 33 字节  Bob 压缩公钥（recipient）
    ac                 OP_CHECKSIG
    68                 OP_ENDIF

注意：参数顺序不可颠倒。CScript(list) 的语义是"列表靠后的元素最后入栈、位于栈顶"，
所以 coinExchangeScriptSig2 虽然参数写作 (sig_sender, sig_recipient)，返回的列表必须是
[sig_recipient, sig_sender, OP_FALSE]，才能使 sig_sender 先与 pk_sender 配对验证。

1.3 两条执行路径的栈推演

(1) 哈希锁分支 —— 接收方（Bob）知道 x 时赎回

    ScriptSig: [sig_bob, x, OP_TRUE]
    执行过程：
        栈 = sig_bob | x | true
        OP_IF 弹出 true ────────────────────> 进入 IF 分支
        栈 = sig_bob | x
        OP_HASH160 对 x 求哈希 ─────────────> 栈 = sig_bob | H(x)
        PUSH H(x) 后 OP_EQUALVERIFY 比较 ──> 相等则继续，否则脚本失败
        栈 = sig_bob
        PUSH pk_bob, OP_CHECKSIG ──────────> 用 Bob 公钥验证 Bob 签名 ──> 真

    结果：只要 Bob 持有正确的 x 并能签名，就能花掉这笔 UTXO。

(2) 双签退款分支 —— 发送方（Alice）与接收方（Bob）都签名时取回

    ScriptSig: [sig_bob, sig_alice, OP_FALSE]
    执行过程：
        栈 = sig_bob | sig_alice | false
        OP_IF 弹出 false ───────────────────> 进入 ELSE 分支
        栈 = sig_bob | sig_alice
        PUSH pk_alice, OP_CHECKSIGVERIFY ──> 用 Alice 公钥验证 sig_alice ──> 真则继续
        栈 = sig_bob
        PUSH pk_bob, OP_CHECKSIG ──────────> 用 Bob 公钥验证 sig_bob ──> 真

    结果：两人都签名时，这笔 UTXO 可以被花掉（本作业中用于超时退款）。

1.4 为什么用 OP_CHECKSIGVERIFY + OP_CHECKSIG 而不是 OP_2 OP_CHECKMULTISIG

    OP_CHECKMULTISIG 有一个历史遗留缺陷：执行时会多弹出一个栈元素，因此 ScriptSig
    必须在末尾额外压入一个 dummy 值 OP_0，且签名顺序必须与公钥顺序严格一致，否则验证
    直接失败。而这里只需要"两个签名都要有效"，用 CHECKSIGVERIFY 串联两次单签即可达成
    完全等价的效果，栈的布局更直观，也不会踩到 dummy 元素的坑。

1.5 时间锁不在脚本里

    coinExchangeScript 的函数签名中没有 locktime 参数，因此无法把
    OP_CHECKLOCKTIMEVERIFY 写入脚本。本方案的时间锁由退款交易自身的 nLockTime 字段承担：
    退款交易被构造时就设定了 nLockTime = 当前链高度 + 锁定期，在该高度之前矿工不会打包它，
    从而形成"期限内不能退、期限后可以退"的约束。

    实测退款交易的 nLockTime：
        Alice（BTC）：4,997,975 = 4,997,970 + 5
        Bob  （BCY）：2,611,497 = 2,611,494 + 3

二、Alice 为什么总能拿回钱？为什么不能简单用 1/2 multisig？（对应练习 B）
================================================================================

2.1 Alice 总有退路的原因

    以 Alice 用 coinExchangeScript 向 Bob 发送 0.1 BTC 为例。关键在于 swap.py 中的
    调用次序：

        第 1 步  Alice 生成交换交易 T1（钱锁在 hash/timeout 脚本里）——但先不广播
        第 2 步  Alice 生成退款交易 T1'（nLockTime = 当前高度 + 5，输出给自己）——也不广播
        第 3 步  Alice 请 Bob 对 T1' 签名，拿回 bob_signature_BTC
        第 4 步  Alice 确认拿到 Bob 的签名之后，才广播 T1

    也就是说，"把钱锁进去"这个动作，发生在"已经拿到退款所需签名"之后。于是：

        - 退款交易 T1' 走的是 ELSE 分支，需要 Alice 与 Bob 两个签名。
        - Alice 在第 3 步已经持有 Bob 的签名，她自己随时能补上自己的那一个。
        - 因此等 nLockTime 到期（高度 4,997,975 之后），Alice 可以单方面广播 T1'，
          把 0.098 BTC 收回自己的地址，完全不需要 Bob 在线或配合。

    所以"总能拿回"成立的条件有三条，缺一不可：
        (i)   退款交易在广播交换交易之前就已签好（时序保证）
        (ii)  退款交易带 nLockTime，期限内不可用，避免她一边锁币一边立刻撤资，
              给 Bob 留出足额的赎回时间窗
        (iii) 退款分支只需发送方 + 接收方两个签名，不需要 x——即使 x 永远不公开，
              退款路径依然可用

    若 Bob 老实赎回，x 就会出现在 T1 的 ScriptSig 中并被写入区块链；Alice 拿到 x 后
    去 BCY 链赎回 Bob 的币。若 Bob 不赎回，则 5 个区块后 Alice 取回自己的币。两条路
    都通向"Alice 不亏"。

2.2 简单 1/2 multisig 无法解决这个问题

    "1/2 multisig"指 2 个参与方中任意 1 方签名即可花费。它无法胜任跨链原子交换，原因
    有三层：

    (1) 缺少哈希锁，两条链之间没有任何密码学绑定
        原子性来自"同一把钥匙同时打开两把锁"。哈希锁的作用是：当一方在某条链上行使
        花费权时，必须把 x 明文写进交易的 ScriptSig，从而**强制公开**秘密；另一方读到
        x 后立刻在另一条链上复用它。1/2 multisig 里没有 x 这个共享变量，两条链上的两笔
        交易彼此独立，"我在这条链拿钱"完全不会触发"你在那条链也能拿钱"。

    (2) 若两笔都设成 2-of-2，协议会卡死
        双方互相等待对方先动：Alice 不广播，Bob 也不广播。更糟的是任一方可以单方面拒绝
        签名使协议永久停滞。没有时间锁时，已经锁进脚本的币将永久无法取出；即便加上时间
        锁，2-of-2 也只是"要么双方都同意、要么都等待"，本质上退化成普通的托管合约，失去
        了"单方即可完成赎回"的原子性。

    (3) 若放宽成 1-of-2，则先动者恒占优势，等价于诈骗
        Alice 可以在 BCY 链上先花掉 Bob 给的币（她只需自己签名），然后拒绝在 BTC 链上
        履行；或者反向操作。由于没有任何机制强迫她把 x 交出来、也没有机制让 Bob 追回
        她已花掉的 BCY，最后一定是"谁先动谁安全，后动者损失本金"。

    结论：原子性不是由多签的门限值提供的，而是由"哈希锁（把两笔交易绑成一体）+
    时间锁（给守约方留退路）"的组合提供的。单靠多签无论 1/2 还是 2/2 都无法建立跨链的
    互不信任信任关系。

3.2 先后次序

    实际的完整时序是：

      Alice 侧                                      Bob 侧
      ---------------------------------------------------------------------
      1. 生成 H(x)，自己持有 x
      2. 构造 T1（不广播）
      3. 构造 T1'（nLockTime=H_btc+5，不广播）
      ----------------------------------------------> 4. Bob 对 T1' 签名
      5. 收下 bob_signature_BTC
      ----------------------------------------------> 6. 构造 T2、T2'
      7. 广播 T1                                     （此时 Alice 的币已锁定）
      8. Alice 对 T2' 签名，交给 Bob
                                                     9. Bob 广播 T2
     10. Alice 用 x 赎回 T2（生成 T4）—— x 随之上链
                                                     11. Bob 从链上读出 x，赎回 T1（生成 T3）

    关键约束：**签名永远先于广播**。任何一方把自己要广播的交易发出去之前，必须已经拿到
    对方对自己退款交易的签名。这样即使对方此后彻底失联，自己也有条可用的退款后路。

3.3 设计原理

    (1) 为什么退款交易也要双签，而不让发送方单签就好？
        如果退款只需 Alice 单签，那么 Alice 可以做这样一件事：先广播 T1 让 Bob 看到币，
        然后立刻广播 T1' 把币撤回来，Bob 还没反应过来 x 就作废了。要求 Bob 也签名，
        相当于让 Bob 在"同意这笔退款会生效"这件事上留下抵押：Alice 一旦撤资，Bob 那份
        签名也就跟着生效了，但 Bob 并无损失；反过来，若 Bob 想赖账，他也无法独自撤回 T2。

    (2) 为什么 alice_locktime 必须大于 bob_locktime？
        两条链的出块速度不同，谁先到期谁就获得"可以先撤"的主动权。令 Bob 的退款窗口
        （3 块）先于 Alice 的（5 块）到期，实际效果是**给 Alice 更长的赎回窗口**：
        Alice 在前 5 块内任何时刻赎回 BCY 都还来得及，而 Bob 必须等到第 3 块之后才能撤。
        如果反过来（Alice 的窗口更短），就可能出现"Alice 还没赎，Bob 已经撤资走人"的
        竞态，原子性被破坏。所以注释里写的是 alice_locktime MUST be > bob_locktime。

    (3) 为什么用绝对高度而不是相对时间？
        作业框架给的是 nLockTime（绝对锁），语义是"该高度之前交易不合法"。用它配合
        "当前链高度 + 偏移"来构造，等价于相对延迟，但实现更简单，也便于本地验证时直接
        比较数值。代价是高度必须填对，因此注释里提示要去 live.blockcypher.com 查实时高度
        （模板中 2018 年的旧值 1,439,691 / 2,062,296 已过期，本文使用实测的
        4,997,970 / 2,611,494）。

四、成功与失败时的数字货币流转（对应练习 D）

4.1 成功：双方都诚实，x 正常公开（alice_redeems = True）

    BTC 链                                          BCY 链
    ----------                                      ----------
    Alice 地址
       |  T0 充值
       v
    T1 交换交易 ──(0.099 BTC 锁入脚本)          Bob 地址
       |                                            |  T2 充值
       |                                            v
       |                                        T2 交换交易 ──(0.009 BCY 锁入脚本)
       |                                            |
       |                                            |  Alice 持 x，生成 T4
       |                                            v
       |                                        T4 赎回交易
       |                                        x 明文写入 ScriptSig
       |                                        BCY 归 Alice
       |                                            |
       +<──────────── x 从 BCY 链上被读出 ──────────┘
       |
       v
    T3 赎回交易（Bob 用同一 x）
    0.098 BTC 归 Bob

    最终结果：
        Alice：付出 0.1 BTC，得到 0.008 BCY
        Bob  ：付出 0.01 BCY，得到 0.098 BTC
        两条链各完成一次所有权转移，且双方都无需信任对方的善意。

    原子性体现在：x 只有在上链时才会公开。Alice 一旦赎回 BCY，x 就永久留在 BCY 链上，
    Bob 随时可以拿去花 BTC 那笔；反过来如果 Alice 迟迟不赎，Bob 也不损失什么。

4.2 失败：一方不赎回，走退款通道（alice_redeems = False）

    BTC 链                                          BCY 链
    ----------                                      ----------
    T1 交换交易（币锁住）                        T2 交换交易（币锁住）
       |                                            |
       |  x 从头到尾没有上链                          |
       |                                            |
       | 等待至高度 4,997,975                         | 等待至高度 2,611,497
       v                                            v
    T1' 退款交易                                 T2' 退款交易
    Alice + Bob 双签                             Bob + Alice 双签
    0.098 BTC 归 Alice                           0.008 BCY 归 Bob

    最终结果：双方各自拿回本金，只损失了 tx_fee（各 0.002 的手续费差额留在交易里）。
    秘密 x 始终没有离开 Alice 的本地内存，因此两条链上的交换脚本都只能走 ELSE 分支，
    哈希锁分支永远无法被触发。

4.3 恶意情形分析（为什么不能单方获利）

    情形 1：Alice 赎回 BCY 后想赖掉 BTC？
        不可能。她赎回 BCY 时 x 已经写进 BCY 链的交易，Bob 读到即可以用 x 花掉 BTC 那笔，
        这不需要 Alice 配合。Alice 赖账的唯一办法是永远不赎 BCY，但那样她一分钱也拿不到。

    情形 2：Bob 拿到 x 后不赎回 BTC，反而去抢 BCY？
        无意义。T2 的哈希锁分支只认"接收方 = Alice"的签名，Bob 是发送方，他的公钥只能
        走 ELSE 分支且需要 Alice 签名。他既赎不走 BCY，也不影响 Alice 已经到手的钱。

    情形 3：Alice 广播 T1 后立刻想撤回？
        她能用的只有 T1'，而 T1' 的 nLockTime 是 4,997,975，期限未到时矿工不会打包，
        且它还需要 Bob 的签名——Bob 完全可以不提供。等期限到了，Bob 早就有机会赎回。

    情形 4：某一方在 x 已公开后同时抢两条链？
        抢不到。同一个 x 在同一时刻对双方等价，但两条链上的脚本把"谁能花"写死了：
        BTC 锁给 Bob（哈希分支）+ Alice/Bob（退款分支），BCY 锁给 Alice（哈希分支）+
        Bob/Alice（退款分支）。x 只解锁对方那条链，自己的链仍需自己的签名。

    这几种情形合起来说明了本方案的核心性质：**任何一方都无法在对方受损的前提下获利，
    因此理性的双方都会选择完成交换**。

5.1 两条分支的运行结果

    两个分支均以 python swap.py 在 broadcast_transactions=False 下运行，退出码 0，
    全程无异常、无网络请求。

    分支一  alice_redeems = True   （见 run_redeem.txt）
        Alice swap tx (BTC) created successfully!
        Bob swap tx (BCY) created successfully!
        Alice redeem from swap tx (BCY) created successfully!
        Bob redeem from swap tx (BTC) created successfully!

    分支二  alice_redeems = False  （见 run_refund.txt）
        Alice swap tx (BTC) created successfully!
        Bob swap tx (BCY) created successfully!
        Bob return coins (BCY) tx created successfully!
        Alice return coins tx (BTC) created successfully!

    两条分支各触发 4 次 VerifyScript（各自两条链的交换交易输入各 1 次，赎回或退款路径
    各 1 次），合计 8 次全部返回真，说明 ScriptSig + ScriptPubKey 的组合在本地是有效的。

5.2 脚本的负向用例

    为避免"能通过就算对"的误判，额外对 coinExchangeScript 做了 5 组反例，均按预期失败：

        错误 secret                -> OP_EQUALVERIFY failed
        退款分支只给单签           -> OP_CHECKSIGVERIFY failed
        用错公钥走哈希分支         -> scriptPubKey returned false
        Sig2 的两个签名对调        -> OP_CHECKSIGVERIFY failed
        空 scriptSig               -> missing arguments for OP_IF

    另有 5 组结构性断言通过：交换输出金额 0.099 BTC、退款输出金额 0.098 BTC、
    Bob 侧交换输出 0.009 BCY、Alice 的 nLockTime（4,997,975）严格大于 Bob 的
    （2,611,497）、ScriptPubKey 首字节为 OP_IF 且末字节为 OP_ENDIF。

5.3 结论

    练习 A（ScriptPubKey）、练习 B（两个 ScriptSig）已实现并通过正向与负向验证；
    练习 C 的两条分支均可在纯本地环境下复现；本文件即练习 D 的交付内容。
